# 还能怎么分析：从数字走到下一步

这份文档不是路线图，而是**一套挑指标的方法**，外加一批已经想清楚的具体候选。

出发点是一句自我约束的话：

> 一个指标值不值得做，只看它能不能推出**不同的动作**。
> 两个指标如果指向同一个「然后呢」，只留一个。

「无效步 866」这种数字的问题不在不准，而在**它没有指向**——用户看完只会点头，
不会去做任何事。所以这份文档里每个条目都必须回答四件事：回答什么问题、用什么事件、
输出长什么样、**看完了能点哪个按钮**。

---

## 一、分析谱系：三层，信息量递增

```text
① 描述  「发生了什么」        计数 / 占比 / 排行 / 时间序列
         例：pwsh 14.3% 失败，退出码非 0 最多
         ↓  能定位，但不能指导
② 转移  「然后发生了什么」    状态转移 / 动作 × 结果 / 连败长度 / 位置分布
         例：失败后换工具 92% 成功，改参数 74%
         ↓  能指导，但证明不了
③ 反事实「不这么做会怎样」    对照 / 变点检测 / 分桶归因 / 前置条件缺失
         例：加一条「edit 前必须 read」后，tool-usage 类失败从 67 降到 9
```

插件当前停在 **②**。这不是能力上限，而是刻意的：③ 需要跨时间的因果证据，
在没有对照组的日志里只能做到「像因果」，讲得太满会误导。

一句话概括这条谱系的代价：**① 让人焦虑，② 让人行动，③ 让人相信行动有效**。
只想做一件事的话，做 ②——因为它是唯一「看完就知道下一步干什么」的一层。

---

## 二、已经落地的那一个：失败回合

选它的理由，用决策检验走一遍：

| 问题 | 回答 |
|---|---|
| 它回答什么 | 失败之后 agent 有没有自救，用的什么方式，管不管用 |
| 为什么不是「重试率」 | 733 个回合里字节级原样重试 **0** 次，指标恒为 0，没有区分度 |
| 换成什么 | **动作分布 × 动作后的成功率**（二维表，不是标量） |
| 输出长什么样 | `改参数 420 次 → 74% 成功`、`换工具 288 次 → 92% 成功` |
| 指向什么动作 | 「失败时更该换路子」——这条可以写进提示词，也可以做成交互约束 |
| 陷阱 | 相关性不是因果：能换工具的场景本来可能就更好修 |

判定细则见 [TAXONOMY.md 第三节](TAXONOMY.md)。这里只强调设计上的一件事：

**它是「转移」，不是「计数」。** 计数告诉你 `pwsh` 失败 414 次；转移告诉你
`pwsh` 失败之后有 76% 的下一步能成功、24% 继续烂下去。同一个工具，
后一个数字才能决定「该修工具，还是该修 agent 用工具的方式」。

## 三、候选清单（按从易到难的链路排序）

每一条都是可独立实现的，前一条不需要后一条。**按这个顺序做，收益递减最慢。**

### 3.1 连败长度（failure streak）

**问题**：agent 陷进去有多深？单次失败是噪声，连续 5 次失败才是事故。

**数据**：`tool/result` 的失败标记按 step 序列累积，遇到任一步全成功就归零。

**输出**：连败长度直方图 `1次 61% / 2次 24% / 3次 9% / ≥4次 6%`，
外加「最长连败 7 步，发生在会话 `xxx` 第 42 步」。

**下一步**：点「最长连败」→ 跳到那一段，生成 prompt：

```text
从第 42 步起你连续 7 次失败（命令超时 4 次、路径不存在 3 次）。
请回看这 7 步：哪一步开始你的假设就错了？当时有什么信息能让你更早发现？
不要重跑，只做归因。
```

**陷阱**：并行调用会让「连续」的判定含糊（同一步里 3 个失败算 1 还是 3？），
建议按 step 计（与本插件口径一致），并在文档里说明。

---

### 3.2 位置分布：失败发生在轮的哪里

**问题**：是开局信息不足，还是收尾验证塌了？

**数据**：把每个失败 step 的序号归一化成「轮内相对位置」（`i / n`），分 10 桶。

**输出**：一条横向分布条。两种典型形状，结论完全相反：

```text
开局型   ██████████▏▏▏▏▏▏▏          前 20% 占 60% → 缺前置信息，该补 explore / read
收尾型   ▏▏▏▏▏▏▏▏██████████          后 20% 占 50% → 验证/交付环节不稳，该改校验脚本
双峰     ████▏▏▏▏▏▏▏████            探索和验证都贵，中间反而顺
```

**为什么值得做**：这是**零新增数据**、只换一个切法就能得到的结论。
同一份事件，切法不同，修的地方不同——这是「分析方法」本身产生价值的最好例子。

**下一步**：直接对应到提示词改动（「先 explore 再动手」vs「交付前必须自检」）。

---

### 3.3 可预防失败：失败前缺少前置信息

**问题**：哪些失败是**本来可以避免的**——不是工具坏了，而是 agent 没先读就动手。

**数据**：对每个失败调用，回看同一轮内更早的 `tool/call`，检查「信息前置条件」：

| 失败类型 | 前置条件 | 缺失即「可预防」 |
|---|---|---|
| `edit` / `write` 的 `tool-usage`（file has not been read） | 先前有对同一路径的 `read` | 是 |
| `path-missing` | 先前有 `glob`/`ls` 确认过路径 | 是 |
| `tool-usage`（invalid argument） | 先前有该工具的成功调用 | 是 |
| `network` / `timeout` / `rate-limit` | —（外部因素） | 否 |

**输出**：`可预防失败 41%（318/779）`，细分到「缺 read 62 / 缺路径确认 189 / 缺调用样例 67」。

**为什么这是最好的一类指标**：它给出的是**规则**，不是数字。可预防 → 加一条约束
→ 下次直接消失。这是唯一能闭环的类别。

**下一步**：一键生成一条可粘贴到 `AGENTS.md` 的规则：

```markdown
- 修改文件前必须先 read 该文件；新建文件前必须先确认目录存在。
```

---

### 3.4 上下文压力与失败的耦合

**问题**：是不是越到后面越容易错？（context rot）

**数据**：把失败 step 的「累积 input token」分桶（0-50k / 50-100k / 100-200k / 200k+），
算每桶的失败率。

**输出**：`0-50k 8% · 50-100k 13% · 100-200k 19% · 200k+ 27%`，若单调上升即强信号。

**下一步**：这是少见的能直接改架构的结论——「长轮次该主动 compact / 拆轮」。

**陷阱**：长轮次本身就是难任务，失败率高可能是任务难度而非上下文长度。
缓解：只在**同一会话内**比较前后段，或控制「轮内工具种类数」这个混淆变量。
讲结论时必须带上这句限定，否则就是过度解读。

---

### 3.5 参数抖动（argument churn）

**问题**：agent 是在「换路子」还是在「同一个坑里换姿势」？

**数据**：对同一工具、同一语义主键（路径 / 命令首词 / URL 的 host+path / 正则），
收集所有参数变体，算变体数与「参数差异字段」。

**输出**：`pwsh · Get-Content config.json：5 个变体，全部超时` →
说明不是参数问题，是这个操作本身不行。

**下一步**：prompt 里直接点出「这个操作你试了 5 个变体都失败，说明方向错了，
请换一个信息源」。这比泛泛的「请重试」有效得多。

**为什么排在后面**：语义主键的提取是启发式的（同一条命令可能有 8 种写法），
误判会让人不信任整张表。等前面几项稳定了再做。

---

### 3.6 审批摩擦

**问题**：agent 请求的动作有多少超出了用户预期？

**数据**：`approval/decided.outcome ∈ {rejected, cancelled}` 的比率与对应动作。

**输出**：`审批被拒 3 / 41 次（7%）`，列出被拒的动作类型。

**下一步**：「被拒 3 次都是 `git push --force`」→ 写进项目规则，一次解决。

**现状**：本机样本只有 3 次，样本量不足以下结论，**先放着不实现**。
这是「不值得做」的判断示例：指标本身很好，但数据不够，做了也是噪声。

---

### 3.7 单位成本：每次成功交付花多少

**问题**：整体效率有没有变好？（端到端，比浪费占比更接近体感）

**数据**：`总 token / 成功完成的轮次数`、`总墙钟 / 成功轮次数`。

**输出**：`每轮成功交付 1.24M token、38 分钟`，配时间序列。

**陷阱**（这条最危险）：分母可以操纵。把失败轮次排除掉，单位成本立刻变好看；
把「成功」定义放宽（有输出就算成功），也立刻变好看。
**必须先固定「成功 = turn/end.reason.kind === 'completed'」再算**，并在页面上写明定义。

---

### 3.8 会话画像聚类

**问题**：我的会话都是什么形状？

**数据**：每会话取 `(步数, 失败率, 恢复率, 平均步时长, 工具种类数, 轮数)` 六维，k-means（k=4）。

**输出**：

```text
一次就成  52%   中位 6 步 · 失败 4% · 恢复 —      ← 短任务，健康
反复试    31%   中位 21 步 · 失败 18% · 恢复 71%  ← 主要优化目标
长跑      12%   中位 68 步 · 失败 11% · 恢复 84%  ← 探索型，正常但要盯成本
崩坏       5%   中位 44 步 · 失败 34% · 恢复 38%  ← 事故，样本价值最高
```

**为什么有用**：聚合数字无感，画像有感。「你 5% 的会话处于崩坏型」比
「平均失败率 15%」更能让人去点开看那 5%。

**下一步**：点「崩坏」→ 列出那批会话 → 一次性生成 5 条 prompt 让 agent 逐个复盘。

**成本**：聚类要标定与解释，是这份清单里最重的一项。**建议最后做**。

## 四、把数字变成动作：六种交接方式

这一步是整份文档的重点。**分析做完了但用户还得自己去描述问题，等于没做。**

插件侧的原则：**不调模型，只把问题快照写清楚**。LLM 的工作留给用户手里的那个 agent——
它本来就在对话框里，而且它能看到现场。

### 4.1 问题快照 → 草稿（已实现）

把数字压成一段自带上下文的排查指令，写进输入框但**不自动发送**。

做得好的关键不是文采，而是**给锚点**：

```text
请复盘本机最近 30 天的工具失败情况（DSH 会话语料，150 个会话 / 5782 步）。

已知：无效步 866（15.0%），失败调用 526，其中命令失败 366、模型重试 140。
失败回合 733：下一步成功 78.3%，仍失败 18.3%，放弃 3.4%。
改参数再试 420 次（74% 成功），换工具 288 次（92% 成功）。

请回答：为什么换工具的成功率比改参数高 18 个百分点？给我 3 个可验证的假设，
并指出你希望我提供哪一段具体日志来验证。
```

三个设计要点：

1. **带数字**，让 agent 不用重新统计（省一轮工具调用）；
2. **带开放问题**，而不是「请优化」——后者只会换来一段套话；
3. **要求它反问你**，把一次性问答变成协作。

### 4.2 深链到现场

`session id + step 号` 是最小可用的「跳转参数」。DSH 目前没有稳定的深链协议，
所以退而求其次：把会话文件路径与步号写进 prompt，让 agent 自己去读那一段。

这是**能用就赚到**的做法：一旦宿主提供深链，同一个按钮改成 `href` 即可，prompt 逻辑不用动。

### 4.3 一键开子会话做后台复盘

把「排查任务书」交给 `subagent`：用户继续干活，agent 在后台读日志、出结论。

插件侧仍然只是**写任务书**，不发起 LLM 调用——是否真的开子会话，由用户按下的那个动作决定。

### 4.4 导出成规则（最有杠杆的一种）

分析 → 发现可预防模式 → **写成一条永久约束**，落到 `AGENTS.md` 或项目规则里。

```markdown
- 修改文件前必须先 read；新建文件前必须先确认父目录存在。
- 同一命令连续 2 次超时后，禁止再改参数，必须换信息源。
```

这件事的价值在于：**分析只做一次，收益持续存在**。所有指标里只有这一条能累积。

### 4.5 定时复核（闭环）

把「下周同一指标」做成定时任务，看那条规则到底有没有把 `tool-usage` 类失败压下去。

没有这一步，所有分析都是「一次性感动」。有了它，才谈得上验证。

### 4.6 对照实验钩子

生成一份「改前 / 改后」对照任务书：让 agent 在未来重放同一类任务，比较步数与失败率。

这是唯一能真正上升到谱系 ③（反事实）的路径——但它需要用户配合做两次，
所以要明确提示成本，别让人以为是免费的。

## 五、优先级：信息增益 × 实现成本

```text
增益高 ┤  3.3 可预防失败        3.4 上下文耦合
       │  ★ 规则化，能闭环       （需控制混淆变量）
       │
       │  3.1 连败长度   3.2 位置分布
       │  ★ 便宜，切法即结论
       │
       │              3.5 参数抖动     3.8 会话画像
增益低 ┤              3.6 审批摩擦     3.7 单位成本
       └──────────────────────────────────────────▶
         低成本                        高成本
```

**推荐顺序**：3.2 → 3.1 → 3.3 → 4.4（规则化）→ 3.4 → 3.5 → 3.8。
3.6 现在别做（样本不足），3.7 只在固定好分母定义后才做。

理由：前两项几乎零成本（数据都在，只是换切法），做完就能立刻改变页面上的结论；
3.3 是唯一能推出「永久规则」的一类，杠杆最大；3.4 需要小心处理混淆，
放在有精力做严谨分析的时候。

## 六、反面清单：会骗人的指标

写在这里是为了**下次想加指标时先过一遍**。

| 反模式 | 长什么样 | 为什么骗人 |
|---|---|---|
| 分母游戏 | 「成功率提升到 92%」 | 减少调用、或把失败轮次踢出分母，都能做到 |
| 幸存者偏差 | 只统计跑完的会话 | 崩掉的会话恰恰是最有价值的那批 |
| 平均值掩盖双峰 | 「平均步时长 4.2s」 | 一半 0.3s 一半 8s，平均毫无意义，要看分位数 |
| 可优化但无意义 | 「token 下降 12%」 | 少打日志、少写注释都能做到，质量没变 |
| 相关性当因果 | 「换工具成功率更高」 | 能换工具的场景本来可能就更好修 |
| 指标太多 | 一屏 12 个数字 | 用户不知道看哪个，等于没有指标 |
| 没有下一步 | 「无效步 866」 | 看完只能点头，不能做任何事 |

最后一条是所有反模式的总纲：**每个数字旁边必须有一个按钮**，否则它只是装饰。

## 七、什么时候该停下来

指标不是越多越好。三个停止信号：

1. **新增指标没有改变任何动作** → 它只是让页面更长。
2. **两个指标的「然后呢」一样** → 留信息密度高的那个。
3. **需要用户先理解口径才能用** → 口径应该藏在文档里，页面上只放结论和按钮。

当前页面上四个 KPI + 两张排行 + 一节转移分析，已经接近「一屏一结论」的上限。
下一步该往里加的不是更多图表，而是**更准的那一个按钮**。
